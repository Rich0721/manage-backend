## III. Requirement Summary

新增四個受保護的產品 API：`POST /productController/addProduct`、`GET /productController/getProducts?productId=...`、`PUT /productController/updateProduct`、`DELETE /productController/deleteProduct`。資料存於 PostgreSQL 的 `tb_products` 與 `tb_labels`；標籤名稱透過 Redis `product:labels` 轉為資料庫中的逗號分隔標籤 ID，產品快取使用 `products:info`。新增、更新與軟刪除後同步產品快取；查詢時僅在快取 key 不存在時從資料庫載入。沿用既有登入驗證並更新 `<uid>:login` TTL。

## IV. Requirement Validation

### 4.1 已確認行為

- `tb_products.id` 是 Unix 毫秒時間的字串，資料庫欄位為 `varchar(13)`；新增時寫入 `created_uid`、`created_at`、`updated_uid`、`updated_at`，後兩欄初值與建立者／建立時間一致。
- 產品的 `label_names` 以逗號分割，從 `product:labels` 對應為 `label_ids`，以相同順序寫入資料庫。Key 不存在時載入 `tb_labels`；有標籤缺漏時清空並重新載入一次；仍找不到即拒絕新增，Gherkin 指定 HTTP 400、`Product label does not exist`，且不得寫入產品或更新產品快取。
- `product:labels` 無過期時間；`products:info` 是所有產品的快取快照，包含 `delete_flag=true` 的資料。多使用者更新快取時需處理並行一致性。
- `getProducts` 將 `productId` 轉大寫；`ALL` 返回所有未刪除產品，單筆及全部都以陣列回傳；查無產品需回傳錯誤。讀取時僅以 `products:info` key 是否存在判斷載入來源，不以單筆未命中啟動資料庫回填。
- 更新要求 `id`、`name`、`label_names`、`cost`、`price`；後四欄不可為空。更新成功寫入 Header `uid` 與程式時間，並同步快取。刪除只設定 `delete_flag=true`，不得執行 SQL `DELETE`。
- 四個 API 必須驗證登入狀態與相應權限；無權限依此需求回傳 401/`Unauthorized`。成功的 response `body.auth` 包含 `uid`、`authorization`，並與 HTTP response header 同步。
- 使用者已確認：產品 API 從 HTTP Header 的 `uid`、`Authorization` 驗證；`delete_flag=true` 的產品對單筆查詢、再次更新及再次刪除均視為不存在。`admin`、`manager`、`user` 都可查詢、新增、更新及刪除產品。
- 刪除時同步更新 `updated_uid`、`updated_at`；`label_names` 各項去除兩側空白後不區分大小寫比對 `tb_labels.name`；產品 API 在 `DEBUG=true` 且缺少 Authorization 時沿用既有 `AuthorizationService` 旁路（仍需 `uid` 與現有角色）。
- 新增產品 ID 衝突回 409/`Conflict`；產品查詢、更新、刪除時產品不存在回 404/`Not Found`。產品 ID 為 13 位 Unix 毫秒字串，四份情境的產品 ID 範例已統一為 13 位。
- 產品標籤必須有值，但本功能不建立、編輯或刪除標籤；從 `tb_labels` 載入既有標籤並解析，找不到時依既有流程重載一次後拒絕產品寫入。
- 使用者最新確認 `tb_labels.id` 是由 PostgreSQL 自動遞增的 `int`；`label_ids` 儲存十進位 ID 以逗號連接的文字（例如 `1,2`），不使用產品的 13 位時間戳格式。`ALL` 必須排除 `delete_flag=true`。
- 使用者再次確認：`products:info` 快取保存全部產品（含 `delete_flag=true`），只有 `ALL` API 回應及指定單筆查詢時依軟刪除規則過濾；快取缺失後從 DB 重建亦須保存全部產品。

## VI. System Design

### 6.1 API and validation

- 四條 route 使用 `/productController` prefix，方法及路徑完全依需求。POST/PUT/DELETE 的 request body 僅承載產品 `body.info`（保留既有 envelope 形狀），GET 不要求 request body；四者授權都從 HTTP `uid`、`Authorization` header 讀入，組成 `AuthorizationObject` 交由 `AuthorizationService`，不複製 JWT／Redis session 驗證。Response 維持既有 `header`、`body.auth`、`body.info` envelope；GET 的 `body.info` 固定為產品陣列。Request body 若仍有 `body.auth`，不得以其覆寫 HTTP Header 的授權身分。
- `AddProductRequestInfo`、`UpdateProductRequestInfo`、`DeleteProductRequestInfo` 使用明確 Pydantic 欄位；`GetProducts` 使用 `productId` query alias。以 Schema 驗證必填、型別、13 位 ID（`ALL` 特例）、`varchar(255)` 長度、金額符合 `numeric(10,2)`；成本及價格 `0` 為有效值，不以 falsy 判斷空值。新增與更新的 `label_names` 必須含至少一個非空名稱；以逗號分割、各項去兩側空白後不區分大小寫比對。空項會無法對應標籤 ID 而拒絕產品寫入；需求未要求去重，依輸入順序保留重複標籤的 ID。
- 產品 response 對外只有需求列出的欄位：新增回 `id`、`name`、`label_names`、`cost`、`price`；查詢、更新、刪除回前述欄位加 `delete_flag`、`updated_user`、`updated_at`。DB `updated_uid` 由 mapping 轉為 `updated_user`。金額 JSON 輸出為數值，時間沿用 Pydantic datetime 序列化。
- 延用 User Manager 的成功 envelope 與 response Authorization header 同步。缺失或無效 token、session mismatch 分別沿用 `AuthorizationService` 錯誤；產品角色拒絕映射到需求指定的 401/`Unauthorized`，不能改變 User Manager 既有 403 契約。Request 資料錯誤沿用 422；產品不存在回 404/`Not Found`，新增產品 ID 衝突回 409/`Conflict`；資料庫／Redis 失效用現有 503 路徑。標籤不存在依 Gherkin 用 400 與 `Product label does not exist`。其他未被 PM 指定的文案不寫成新業務規則。
- 每個成功操作呼叫 `refresh_session()` 更新 `<uid>:login` 到期時間；失敗不將其宣告為成功。`DEBUG=true` 且缺少 Authorization 時沿用既有旁路；必須提供 uid 並載入現有使用者，現有角色檢查仍執行。若 token 有值，即使 DEBUG=true 也走完整 JWT／Redis 驗證。

### 6.2 PostgreSQL

- `database/DDL/tables/TB_PRODUCTS.sql`：`tb_products(id varchar(13) PRIMARY KEY, name varchar(255), label_ids text, cost numeric(10,2), price numeric(10,2), delete_flag boolean DEFAULT false, created_uid varchar(255), created_at timestamp, updated_uid varchar(255), updated_at timestamp)`；必要欄位 `NOT NULL`、table/column comments，時間由應用程式提供而非 `DEFAULT`。
- `database/DDL/tables/TB_LABELS.sql`：`tb_labels(id integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY, name varchar(255), created_uid varchar(255), created_at timestamp, updated_uid varchar(255), updated_at timestamp)`；必要欄位 `NOT NULL`、comments。PostgreSQL 自動產生整數 ID，本功能只讀取，不自行呼叫新增標籤。使用 `BY DEFAULT` 可讓測試資料明確指定需求範例中的 `1`、`2`，正式新增仍可由資料庫遞增。名稱未定義 unique constraint，本次不添加標籤寫入規則；若既有資料出現標準化後同名而對應不同 ID，解析應明確失敗並記錄資料異常，不得任選其一。
- `src/models/po/product.py` 的 `ProductPO`、`src/models/po/label.py` 的 `LabelPO` 與 DDL 欄位一致。`ProductRepository` 提供 insert、get_by_id、list_all、update、soft_delete，使用參數化 SQL 與 `RETURNING`／row count 判斷不存在；更新與軟刪除必須以 `id` 且 `delete_flag=false` 為條件，避免已刪除產品在並行操作中被改動，不執行物理刪除。`LabelRepository.list_all()` 一次取得標籤資料。沿用現有 pool、transaction 與 repository exception 寫法。
- 毫秒 timestamp 在單一毫秒多次新增可能碰撞；DB primary key 必須拒絕重複並回 409/`Conflict`，禁止覆蓋現有產品或默默更改 ID。

### 6.3 Redis and consistency

- `product:labels` 存完整名稱至整數 ID 的映射，無 TTL。比對鍵以 Python `strip().casefold()` 標準化；回傳 `label_names` 應使用 `tb_labels` 的正式名稱。Redis 序列化／讀取須保留整數語意，將 ID 寫入 `label_ids` 時才轉成十進位字串。無 key 時從 `tb_labels` 載入；缺漏時至多重新載入一次，再確認全部名稱可解析。重載須以 Redis lock 或等效原子協調方式保護整個 key 的替換，避免先清空後被另一請求讀到部分資料。空表的快取表示法必須能區分「已載入但空」與 key 不存在；若 DB 有兩筆標籤標準化後同名而指向不同 ID，應回報資料異常，不得任選其一。
- `products:info` 存所有產品的完整快照，含軟刪除記錄；對外查詢時再依 `delete_flag` 過濾。快照應用 JSON 等現有 Redis client 可處理格式，明確保存 Decimal、datetime 與 label 名稱，重讀後須還原成一致型別；空清單也需保留「已載入」狀態。快取沒有需求指定的 TTL，不自行設定。
- 讀取時僅於 key 不存在時由 `ProductRepository.list_all()` 載入並原子替換；key 存在但查無指定 ID 時直接回不存在，不自行刷新。新增／更新／軟刪除成功後由寫入流程同步刷新快照，不依賴查詢端修正舊資料。
- 多使用者寫入與首次載入共用 `products:info` 專用 lock；鎖內重新確認 key／DB 狀態。寫入流程在鎖內先讓舊快照失效，失效成功才執行 DB 異動並 commit，之後重建完整快照並原子替換 Redis value；首次載入於相同鎖內 double-check，避免在寫入中途載入舊資料。若 DB 失敗，key 維持缺失並於下一次讀取重建；若 DB 已 commit 但快照發布失敗，key 保持缺失、回 503 並記錄可追查的產品 ID／操作，下一次讀取從 DB 重建。鎖需有有限 lease、取得逾時、必要的續租及安全釋放機制；不得以無限等待阻塞 API。`product:labels` 使用獨立 lock。PostgreSQL 和 Redis 無共同 transaction，錯誤回應不得宣稱 DB 已 rollback；若鎖／Redis 在失效舊 key 前不可用，必須中止 DB 異動。

### 6.4 Security, errors, logging

- Token 驗證使用現有 `AuthorizationService`，操作者由 `UserRepository.get_by_uid()` 載入；不得信任 client 傳入的 `updated_user`、時間或權限。`admin`、`manager`、`user` 都可執行四項產品操作；仍需確認操作者存在、角色是現有三者之一，且登入驗證有效。
- 產品服務錯誤新增至 `src/services/errors.py`，例如標籤不存在、產品不存在、產品權限拒絕、產品 ID 衝突；公開訊息與 HTTP code 依已確認需求，資料庫及 Redis 原始例外不得外洩。
- 使用現有 `logging`；記錄產品 ID、操作、錯誤類型與必要 uid，不記錄 Authorization token、密碼、Redis 連線密碼或完整產品敏感內容。

## XI. Clarifications and Documentation Sync

本版沒有阻擋開發設計的 Open Question。使用者已確認：13 位產品 ID、同 ID 衝突 409、產品不存在 404、`tb_labels.id` 為自動遞增的 `int`、`label_ids` 使用如 `1,2` 的整數 ID 清單字串、標籤必填，以及標籤建立／管理另立需求。產品 ID 與標籤 ID 的產生方式、資料型別分開，不可混用。`products:info` 保存所有產品，包括已軟刪除者；`ALL` API 回應才排除已刪除產品。

前次列出的兩處情境示例已修正：`Get_Products.feature` 第一個 `ALL` 回應不再包含已刪除產品，`Delete_Product.feature` 刪除後的 `updated_at` 已改為新時間。

目前僅有一處情境示例未同步，本計畫記錄實際驗收值，System Design 不直接修改 PM 文件：`Get_Products.feature` 第二個 `ALL` 情境在 Redis key 不存在時，預期新建的 `products:info` 只列兩筆未刪除產品；依使用者最新確認，快取應包含第三筆 `delete_flag=true` 產品，而 API 回應仍只列前兩筆。

技術決策：本功能不去重標籤輸入，逐項解析並依原順序保存 ID；空字串由 Schema 拒絕，含空項或不存在的標籤由解析流程拒絕。既有 `tb_labels` 若有標準化後同名但 ID 不同的資料，視為資料異常而拒絕解析，不自行決定選哪個。產品快取在 DB 異動前於鎖內失效，確保發布失敗時不留舊快照；DB 已 commit 但發布失敗回 503，記錄已提交狀態，下一次查詢自 DB 重建。
