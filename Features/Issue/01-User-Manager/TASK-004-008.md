# TASK-007-008 Implementation Issue

Status: RESOLVED

## Task ID

TASK-007, TASK-008

## Issue

Resolved. PM confirmed that security controls will be improved later and that
current operations should use JSON header.uid to identify a TB_USERS account.

## Existing Behavior

The repository has no application controllers or header.uid-based operator
validation. The PM requirement defines the API contract.

## Plan Definition

TASK-007 and TASK-008 require header.uid to be present and to identify a
TB_USERS record. TASK-008 loads the operator role from TB_USERS and never uses
client-provided Permission for authorization.

## Why Implementation Can Continue

The PM-approved interim behavior intentionally permits account lookup by
header.uid. This plan does not add session, token, or anti-forgery behavior.

## Security Follow-up

UID and Permission forgery prevention, session state, expiry, and revocation
are deferred to a future PM requirement change.

## System Design Review

Status changed from OPEN to RESOLVED.

The latest requirement update resolves these former parts of the issue:

- JSON header-envelope transport is confirmed for all APIs.
- getUsers uid identifies the current operator, and registration Gherkin data
  includes userName.
- The second stage correlates its temporary code using Email.
- Temporary Codes are random six-character alphanumeric values, stored by Email
  in Redis for three minutes, and replaced on resend.
- Passwords are SHA-256 hashed by the client before transmission.
- TB_USERS and registration now define user_name as the non-unique display name
  returned by getUsers.
- Admin accounts are externally provisioned, and the front end must reject
  listing or modifying any admin account, including the current operator.
- The updated requirement no longer defines credential or Temporary Code
  lockouts; those behaviors are removed from the implementation plan.

PM explicitly approved the interim functional rule. Missing or unknown UIDs
are rejected; the database is the source of the operator role; client-provided
Permission is ignored. This permits the documented logout and role-based
operations without asserting that the request identity is secure.

## Non-blocking Security Observation

The current requirement explicitly sends a client-side SHA-256 password value.
That fixed value can be replayed as a credential if captured. This observation
does not change the approved current behavior and is not a reason to implement
a different hashing scheme. PM should record any future server-side password
protection, replay prevention, or authenticated-session requirement as a
separate requirement change before implementation.

The implementation plan was updated on 2026-09-15. TASK-004 through TASK-008
are `PLAN UPDATED`; TASK-007 and TASK-008 may now proceed using the approved
interim header.uid account lookup. Security improvements remain out of scope.

Programmer may implement TASK-007 and TASK-008 according to the updated plan.
